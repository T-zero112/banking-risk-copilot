# Database Schema

`app/sql/schema.sql` initializes an empty PostgreSQL database. It is not a
migration for an existing database. Run it once; existing tables require an
explicit migration. The transaction prevents a partial initialization.

## Data Model

- `customers`: individual or corporate customers, KYC review dates, and due
  diligence level. Nationality uses a two-letter uppercase country code and is
  optional for corporate customers; occupation is optional. Complete KYC must
  have a review date on or after onboarding. This MVP does not track pre-onboarding
  reviews or historical KYC states.
- `accounts`: customer-owned accounts with a balance and currency. Negative
  balances are allowed to represent overdrafts.
- `transactions`: positive amounts with direction generated from transaction
  type. Timestamps include time zones. Counterparty details can be unknown,
  including cash transactions. Account and transaction currencies can differ.
- `risk_scores`: daily customer score snapshots. Synthetic scores are demo
  inputs, not evidence of a validated risk model.
- `alerts`: a reason, optional related transaction, assignee, and resolution
  timestamp. Closed alerts require a resolution timestamp. The application must
  check that a related transaction belongs to the alert's customer; the foreign
  key only checks that the transaction exists.
- `policy_documents`: source and version metadata for each ingested document.
  A SHA-256 content hash distinguishes different versions at the same URL.
- `audit_logs`: request-level questions, generated SQL, execution outcome,
  retrieved references, answers, and errors. A request can have multiple log rows.

## Analytics Assumptions

All MVP accounts are domiciled in Singapore. `is_cross_border` is generated by
comparing the counterparty country with `SG`; an unknown country produces NULL,
not false. Supporting accounts in other countries requires changing this model.

`is_high_risk_country` is a classification snapshot. Populate it together with
`high_risk_country_list_version` using a defined demo list; NULL means not
classified. The flag alone is not a finding of misconduct.

Amounts and balances use three-letter uppercase currency codes. The checks
validate format, not membership in an official code list. Do not sum currencies
together or apply one numeric threshold across currencies. The first synthetic
dataset should use SGD; multi-currency analytics need dated exchange rates and
explicit conversion rules.

Store timestamps with explicit offsets. Queries interpreting calendar dates
should specify `Asia/Singapore`. Synthetic data generation and evaluation should
use a fixed reference time so that last-30-days cases are reproducible.

## RAG and Audit Boundaries

`policy_documents` stores document metadata. The policy retrieval migration adds
`policy_corpora`, `policy_chunks`, and `policy_retrieval_state` for versioned chunks,
an English full-text index, and the active corpus pointer. Embeddings and vector
indexes are not implemented yet. See [retrieval notes](policy-retrieval.md).
Each retrieved reference should
include `document_id`, `content_sha256`, `chunk_id`, and a page or section locator.
The JSONB column requires an array; the application validates each reference's
shape and document identity. Preserve references to the version actually used.

Audit columns record outcomes but do not enforce access control or SQL safety.
Migration 004 grants business/policy SELECT to banking_reader and limited audit
INSERT/UPDATE plus SELECT to banking_audit. Admin handles ingestion/migrations.
A stored `user_role` is context, not proof of authorization. See
[runtime permissions](database-permissions.md).
# Customer Review Audit Migration

`003_customer_review_audit.sql` adds nullable review-specific fields to existing
`audit_logs`, preserving older records: customer_id, review_mode, review_status,
finished_at, elapsed_ms and review_metadata JSONB. A partial unique request_id
index applies only to customer review records. Customer ID deliberately has no
foreign key so unknown-customer failures can also be audited. SQL remains fixed
and parameterized; generated_sql is NULL. Reports are saved as JSON text in
final_answer and policy provenance in retrieved_policy_refs. See
[review audit](review-audit.md) for status, privacy and durability limitations.
